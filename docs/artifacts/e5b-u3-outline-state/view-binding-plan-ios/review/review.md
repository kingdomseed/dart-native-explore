## Why the source plan is admissible

**Selection and native ownership remain intact.** `scene_controller.dart:403–428` emits the batch through the existing command path; `Dart3dPlugin.swift:47–77` copies delivery bytes and queues work; `SceneViewHost.swift:1129–1147,1608–1643` drains and applies it. `SelectionOutline.swift:13` owns the sole color map and has no renderer read path yet. The explicit-load clear, removal clear and deferred-realization prune are present at `SceneViewHost.swift:1410,2021,1177`. The sketch adds derived attachments, not a second authoritative selection map. Settled lifecycle B needs no redesign.

**The consumers really are different native objects.** Single-screen mode uses the host; normal split mode draws every visible screen through sibling SCNViews; diagnostic-channel selection also forces sibling mode even for one screen (`RenderTargets.swift:468–567`). Target views retain individual SCNRenderers and MSAA state. The design assigns a binding to each of those actual consumers and explicitly captures the leading real camera that the ordinary sibling snapshot currently omits (`RenderTargets.swift:609–641`). It does not reuse a host mask across their cameras.

**The technique-copy rule is correctly identified.** Installed `SCNTechnique.h:316` declares a copy property, and both SCNView and SCNRenderer conform to its support protocol. The source installs techniques at `SceneViewHost.swift:462,481,501`. The sketch requires binding the installed copy and rebuilding the combined technique through those owners when it is replaced. That is a sound direction; header conformance does not prove execution, texture-symbol rebinding, or independence of installed copies at runtime.

**The target seam exists, but the crucial SceneKit capability is unknown.** `RenderTargets.swift:387–392` passes an existing command buffer and render-pass descriptor to render-only SCNRenderer rendering, then commits it. A private mask can be proposed before that call without changing target admission. What remains unproven is whether that exact render-only entry point executes a composite-only technique whose COLOR input contains the normal scene, samples the preceding mask from the same command buffer, and writes the supplied single-sample/MSAA destination with the intended final resolve/store. The technique and renderer headers do not establish that entire combination. The design labels it a gate rather than asserting success. Its explicit-Metal alternative is reasonably rejected for this unit because the screen interface exposes an encoder/pass/queue, without the required final command-buffer and post-resolve presentation seam.

**Scheduling and attachment ownership follow current code.** Only `renderDueTargets` admits a target draw (`RenderTargets.swift:262–295`); highlight ingress does not dirty targets, while public render requests do (`SceneViewHost.swift:3092–3104`). Native mesh ownership is primitive zero plus immediate `d3prim:` children (`FsceneRealizer.swift:5205–5251`), and instances use the native baked geometry (`2349–2399`). The design preserves these draws rather than recursively selecting authored descendants. Skin attachment follows the primitive owners (`6731–6822`); private bone/skeleton retention is necessary because the installed skeleton property is weak. The proposed morph capture follows the current presentation-weight/target owners. Immutable publication and per-binding mutable attachments are explicit requirements, not implemented facts.

**Color, coverage and composition match the pinned source policy.** The inspected flutter_scene 0.23.0 encoder substitutes one for exactly zero highlight alpha, passes other components through, and disables mask blending (`object_filter.dart:109–113,158–170`). The mask fragment writes that RGBA. The outline shader chooses greatest neighbor coverage with strict-greater ties, uses the stated thresholds and circular default radius three, and writes opaque contours while preserving base RGBA elsewhere (`flutter_scene_outline.frag:28–59`). Linear clamp sampling and the final display-chain placement are present in the upstream pass and `scene.dart:2754–2773`. The sketch correctly avoids the historical white/gold, preserved-contour-alpha prototype. Provisional rgba16Float storage, representable range, opacity interaction and working-space conversion still need execution evidence.

## What the finite probe can decide

These are operational acceptance criteria for the sketch's existing tests, not additional production machinery.

1. **Per-view binding:** exercise both the host single-screen route and two simultaneous visible siblings, with distinct asymmetric camera silhouettes, layer membership and output sizes. Use real public batches for two different node colors and null clears. Each consumer must show its own expected membership, color and contour; changing one camera must not give another consumer that camera's mask. Read and configure each installed technique after assignment. A result obtained by binding only the host, rendering an independent substitute scene, or inspecting the builder technique does not answer this question. Replacement/rebinding remains open until the actual `applyToneMap`/`applySiblingResolve` and view-rebuild paths have also been exercised.

2. **Manual-target admission:** observe set and clear separately, including a target that already stores a contour. Consume initial dirty draw → set highlight without a render request and verify stored target bytes stay unoutlined → request public render and verify the contour appears → clear without requesting render and verify the old contour remains stored → request render and verify it disappears. Screens must respond during both clean-target phases. Collapsing set and clear before observing the target can return to the original image and falsely pass. Byte preservation proves stored output; a claim that no target encoding occurred additionally needs disposable-instrument observation of the existing due/render path. No public query seam or scheduler change is justified.

3. **Same-buffer target technique:** capture the actual scheduled target's raw output and submitted work for both no-AA and existing MSAA modes. Establish mask-before-normal-render ordering within that buffer, the composite-only tail's execution, and the resolved final target contents. Compare ordinary RGB/alpha outside the reference contour and verify the expected colored opaque contour. Preserve exposure save/restore and the absence of artistic resolve. A separate SCNRenderer demonstration or an added post-scene Metal compositor would test another route.

4. **Screen ordering:** repeated camera/set/clear observations can expose stale and wrong-view masks only if captures retain the changing states of the actual consumer draws. Settled endpoints cannot establish hidden enqueue order. Installed Metal headers describe queue seriality, not SceneKit's enqueue position; didRenderScene is not GPU completion. Accept at most an empirical result for the recorded transitions. Do not insert synchronous waits or change presentation to obtain a pass. If actual-draw observation is unavailable, leave this gate inconclusive.

5. **Shared-scene alignment:** moving cameras alone do not test an ordinary sibling whose base geometry advances after the sampled mask. Before accepting this capability, include an asymmetric moving/deforming selected draw under the existing host update, and compare its base silhouette and contour within the same observed sibling output. Do not freeze the host or substitute W34's detached base for the ordinary shared-scene path. Static preservation comparisons remain a separate frozen-input lane. The sketch explicitly leaves animation alignment open; the initial three-view result cannot close it.

6. **Alpha boundary:** manual target color clears to `(0,0,0,1)` on every view (`RenderTargets.swift:366–385`), so it supplies an opaque baseline only. The private synthetic zero/fractional premultiplied input must traverse the identical tail, shader configuration and relevant attachment encoding being evaluated, with raw RGBA readback. Outside-contour components must be preserved; contour RGB must follow the selected neighbor and alpha must become one. No UI screenshot over black, separate CPU formula or different compositor closes that oracle. Success establishes compositor arithmetic/encoding only. Failure to reach/read this private boundary leaves it unproven; it does not authorize a public transparent-target feature.

The plan can therefore discriminate the initial per-camera, target-admission and compositor failures without changing ownership B. It may return a blocked/inconclusive capability result. That is a legitimate outcome of this investigation, not grounds to introduce a fallback.

## Gates that this PASS leaves open

- **Three physical pixels at reduced screen scale:** current screen quality changes contentScaleFactor, while viewport placement uses device scale (`RenderTargets.swift:688–752`). Output-sized offsets in a low-resolution technique do not establish a three-physical-pixel displayed border. Scale-one evidence must stay bounded to scale one. Reduced-scale acceptance requires observing the real technique raster and a suitable post-upscale placement; production must not silently force scale one.
- **Coverage and evaluated attachments:** selected primitives/batches, reflection and effective culling, hidden ancestors/layers, alpha-zero substitution, fractional/overlapping coverage and working-space colors need their own decisive fixtures. General skin/morph and combined deformation must follow the current native evaluated pose without adding animation or simulation owners. Material displacement and other emitters remain explicit unsupported/unproven cases until their native owners are audited. No undeformed or recursive fallback is acceptable.
- **W34 coexistence:** diagnostic single/split screens must preserve detached base attachments, light/skin/morph ownership, identity resolve and wireframe. Authored targets retain their ordinary render path and schedule. The diagnostic and outline captures must agree on the sampled host boundary; neither may mutate published attachments or the authored scene. Static normal-screen success supplies no W34 result.
- **Retirement:** the two-drain graveyard is an existing heuristic (`SceneViewHost.swift:1032–1040,1127–1141`), not a SceneKit CPU-lifetime or GPU-completion guarantee. Resize, technique/mask replacement, target/view replacement, scene load and detach need observation while relevant old users remain in flight, including CPU lifetime diagnostics and GPU/command-buffer errors where available. Completion of a private mask buffer alone does not certify completion of a hidden screen consumer. No-crash repetitions are bounded evidence, not a lifetime guarantee. If a relevant release/use boundary cannot be observed, keep this gate open; do not add arbitrary drain delays.
- **Android production prerequisite:** remains required before production integration. Android was neither inspected behaviorally nor run, and A142 was not accessed or discovered.
